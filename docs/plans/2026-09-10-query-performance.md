# 服务器查询提速与状态准确性实施计划

## 通俗解释：究竟发生了什么

现在查询某一台陌生服务器，有时必须等其他服务器全部查完才能得到结果；常用服务器也会被官方列表请求拖慢。

这类似打电话问多家店铺营业时间：我们已经接到了目标店铺的答复，却还在等其他店铺接电话。店铺对应游戏服务器，电话对应网络探测，通讯录对应服务器名称与地址的映射。改进后，目标答复一到即可回复；查过的地址会记住，通讯录暂时取不到也能直接联系常用服务器。

例如查询 CN_Swiss_02，现在即使它先返回，也可能被其他超时服务器拖住；改进后只等待它自己的结果。已经缓存的状态继续立即返回，但太旧的结果会明确标注时间，避免把旧人数当作当前人数。

## 专业判断：问题在哪里

本计划依据当前 main.py、warband_net.py、配置和 README 的源码核查。图索引覆盖检查提示文件元数据变化，已直接读取源文件核对。尚无部署环境延迟测量，以下区分确定的执行行为与需要实测的收益。

| 已确认行为 | 对用户的影响 |
| --- | --- |
| 普通缓存命中不等待网络，但冷启动和未知名称分支会等待 | README 的“总是立即返回”不适用于全部场景 |
| probe_many 使用 gather，整批结束才交付结果 | 快服务器等待慢服务器；未知名称无法命中即回 |
| 每轮先拉主列表，失败或为空立即退出 | 固定端点实际仍受官方接口故障影响 |
| 已知主机、固定端点和抽样探测分批等待，下线复核逐台执行 | 刷新耗时叠加；同一端点可能重复探测 |
| 收齐 XML 后继续读取，最多额外等待 0.4 秒 | 服务端不关闭连接时出现不必要的等待 |
| 连接至少允许等待 3 秒；读取逐次重新计时 | probe_timeout 不构成单次探测的完整耗时上限 |
| 所有成功响应的 IP 都加入 _known_hosts | 全量发现后高频刷新范围可能持续扩大 |
| 刷新与发现分别加锁，遇到任务运行时发现直接退出 | 同时查询可能暂时报未识别，且两种任务并不构成统一去重 |
| 使用整轮刷新时间判断缓存新鲜度，部分失败不清除旧记录 | 旧记录可能长期看起来在线、及时 |
| 重启后丢失内存中的端点映射 | 需要再次寻找之前查过的服务器 |

实际耗时还包括 AstrBot 调度和消息平台发送。不能把插件构造回复的耗时等同于 QQ 收到消息的耗时，也不能在没有基准的情况下承诺固定提速倍数。

## 要达到什么目标

- 已缓存查询立即构造回复；单台查询不被无关慢服务器阻塞。
- 常用端点可独立刷新，官方列表故障时仍然可查。
- 刷新、发现和多人查询共享必要的网络工作，限制连接数与后台任务数。
- 明确区分新鲜结果、旧结果、尚未查询、近期无响应和未找到。
- 重载、断网、服务器改名或迁移后能恢复，避免遗留任务和过期状态。
- 保持已有命令、别名、白名单、排除项、默认展示顺序和零新增第三方依赖的使用体验。

本次不引入数据库服务、分布式缓存、WebUI 页面或新的消息平台，不改动 AstrBot 核心，也不将部署、推送或发布版本作为默认实施动作。

## 改进方向

### 一、完整数据到达后立即结束探测

TCP 读取检测到完整 ServerStats 后，仅提取该 XML 文档并立即解析，忽略文档外的尾部内容；分包、前置 HTTP 头和中文字段继续兼容。连接、读取和资源清理使用有界时间，避免每次读取重新获得完整等待额度。用单调时钟计算等待预算，墙上时间仅用于展示和保存时间戳。

保留 HTTP/HTTPS 主列表支持，处理非成功状态和常见响应分帧，包括 Content-Length、chunked 和连接关闭结束；限制响应大小和整体耗时。TLS 上下文在合适的生命周期内复用，不为每次查询重复初始化。完整数据到达即结束，不再依赖对端断开连接。

用户得到的变化：服务器已回答就马上可用，网络异常也不会无限拖延。

### 二、逐条交付结果，查询任务共享探测

将网络批量探测改为逐条交付结果，并在每条完成时更新缓存。未知名称查询带着目标等待，命中即可返回；只在本次候选扫描完成后认定未找到。优先精确匹配，再保留已有简称与模糊匹配规则，避免后到的精确匹配被先到的模糊结果抢走。

建立按端点共享的在途探测任务和全局并发限制。定时刷新、补偿刷新、发现及多人请求复用同一端点任务。一个请求超时或取消不应取消其他请求仍需使用的任务；没有请求需要的任务按明确的生命周期结束。发现请求复用同一轮扫描结果，不能因为锁被占用就直接判定未识别。

未知查询设置前台等待预算；预算用尽则说明仍在查询，后续查询复用结果。默认维持单次回复，不额外异步推送消息。负缓存仅记录完整搜索后的未找到结果，短时复用；搜索中断或网络失败不能记为确定不存在。

用户得到的变化：多人同时查服不会各自重复扫描，目标先返回就先拿到结果。

### 三、常用状态刷新与官方列表发现分开

把刷新拆成已知端点状态更新和低频地址发现。固定端点、配置服务器已知地址、近期查询过的端点优先刷新，官方列表拉取在后台独立执行并缓存。主列表失败时继续使用上次有效列表和已知端点；失败或空列表不能据此把服务器判为下线。

每轮候选端点统一去重，端点复核也在统一并发预算内执行。种子主机用于发现对应地址，不把所有成功响应主机永久升级为高频目标。为临时热门端点设置容量与闲置退出期限，后台抽样保持公平轮转，避免长期遗漏。

状态刷新频率与发现频率分别配置：已有 refresh_interval 继续表示状态刷新间隔，新设主列表刷新间隔。初始保持旧配置兼容，推荐状态刷新 15～30 秒、主列表 2～5 分钟；是否降低默认状态间隔由基准与连接负载决定。周期计算考虑本轮耗时，避免“工作时间加休眠时间”造成刷新越来越稀疏，也避免超时后密集补跑。

用户得到的变化：查常用服务器无需先等官方接口，全网扫描也不会挤占全部查询资源。

### 四、按服务器维护状态与新鲜度

每个端点分别记录最后成功时间、最后尝试时间、连续失败次数和当前状态，整轮刷新成功不能替某条记录续期。短暂失败保留上次成功结果并标记“上次结果”；达到明确失效条件后显示“近期无响应”，不声称已经确认服务器关机。

冷启动尚无数据时显示“正在查询”或“暂无结果”，不直接显示未在线。已有缓存先返回，超龄则合并安排补刷；硬过期后停止把历史人数作为当前状态展示。将 show_offline 对无响应条目的行为写清楚，并保证指定查询始终得到明确结果。

名称与端点分别建索引：名称规范化优先精确命中，端点和端口号按完整值匹配，消除端口尾缀误匹配。改名、迁移和重名时清理或保留必要映射，不能让旧名称永远显示在线。重名端点优先沿用配置或已确认映射，无法唯一定位时展示可区分的端点提示。

展示名单在等待刷新或发现后重新计算，防止本次刚发现的服务器没有出现在“全部”结果中。排除项、查询入口和缓存恢复使用一致的过滤规则。

用户得到的变化：快速回复仍然可信，数据旧、没查完与没响应能一眼区分。

### 五、恢复已知端点并管理任务生命周期

使用 AstrBot 官方插件数据目录保存名称与端点映射；可保存最后一次成功快照，但恢复后必须保留原始时间并按年龄标记，不当成刚查询的数据。采用带版本的轻量 JSON、原子替换和合并写入，避免每次探测都落盘。限制文件大小、记录数量和保留期限；损坏文件跳过并重新发现，不影响插件加载。

按目标 AstrBot 版本核实数据目录与初始化接口。启动及插件重载后都预热，不能仅依赖可能不会再次触发的全局启动事件；同时保留首次查询的兜底启动。统一注册并清理刷新、发现、补偿、探测和持久化任务，卸载后停止写缓存和发送结果。

用户得到的变化：机器人重启后能尽快查到熟悉的服务器，重载不会留下重复刷新任务。

### 六、配置、文档与性能证据同步

保留既有配置名和意义，新增配置控制在主列表间隔、查询等待预算及并发预算等必要项。缓存软过期沿用 max_cache_age；硬过期与发现未命中缓存先用明确、保守的内部策略，确有调整需求再开放配置。校验非法数值并限制上下界，避免小于零、超大并发或错误类型导致后台任务退出。

修正配置提示中“缓存超龄会先刷新再返回”的旧描述，README 按缓存命中、冷启动、已知直查、未知发现分别解释行为。更新版本元数据与变更记录，使兼容性和新增配置可追溯。

增加低噪声统计：主列表耗时、单端点耗时、目标命中耗时、回复构造耗时、缓存年龄、探测次数、任务共享次数及超时数量。日志不逐条刷屏，不记录用户身份或凭据。

用户得到的变化：配置说明与真实行为一致，出现“变慢”时可以定位在哪一段。

## 实施范围与顺序

1. 建立可重复的本地慢服务器场景，记录现有等待行为，明确消息平台耗时不纳入插件本地基准。
2. 完成网络读取边界、整体超时和结果逐条交付，为后续调度提供可靠基础。
3. 接入共享端点探测、目标优先返回、独立主列表缓存和有界后台发现。
4. 整理状态时间、名称映射、冷启动与失败展示，补齐单台与全部查询的一致性。
5. 接入数据目录持久化、重载预热和统一任务清理，验证恢复与取消行为。
6. 同步配置、README、版本和变更记录，完成回归与性能对比；具备运行条件时再做真实 AstrBot 触发验证。

主要修改范围为现有 main.py、warband_net.py、配置与文档；新增有意义的回归测试和轻量测试辅助设施。只有调度逻辑确实难以维护时才提取独立模块，不为了形式拆文件。

## 如何确认完成

| 场景 | 验收结果 |
| --- | --- |
| 完整 XML 到达但服务端保持连接 | 不再出现额外 0.4 秒等待，解析字段保持正确 |
| XML 分包、前置 HTTP 头、文档尾部杂项、无效 XML | 正常输入正确解析，异常输入有界失败 |
| 慢连接、持续分片、异常关闭 | 总探测时间受预算约束，清理有界，无连接泄漏 |
| 主列表非成功状态、分块响应、超大正文或超时 | 正确处理或有界失败，不污染上次有效列表 |
| 目标 0.1 秒返回，其他候选 2 秒返回 | 目标回复明显早于整批扫描完成；受控测试以 0.5 秒为宽松目标，不作为公网 SLA |
| 多个请求同时查询同一端点 | 同一在途端点只发起一次探测，结果被所有等待者复用 |
| 一个等待者取消，其他等待者仍需要结果 | 其他等待者正常完成，任务最终被回收 |
| 主列表不可达或返回空 | 固定端点和已知端点仍更新，不集体误报下线 |
| 后台大范围发现时查询常用服务器 | 并发和队列受限，常用端点不被整轮扫描阻塞 |
| 查询缓存内服务器 | 构造回复不等待网络；记录多轮中位数和 P95，本地隔离基准以 P95 小于 50 毫秒作为目标 |
| 单台持续失败，但其他服务器正常刷新 | 该条目逐步变为旧数据或无响应，不被全局时间续期 |
| 冷启动、缓存损坏、恢复很旧的快照 | 不崩溃、不把未知当离线、不把旧快照当新结果 |
| 服务器改名、迁移、重名、端口尾缀相同 | 结果可定位，无错误别名命中或永久在线的旧记录 |
| 单台查询、全部查询、配置顺序、排除项、白名单 | 保持原有入口与权限约束，新结果及时纳入展示 |
| 完整扫描未找到与扫描中途超时 | 前者可短期复用未找到结果，后者仍允许继续发现 |
| 重载和卸载 | 任务均可停止，重新加载只运行一组调度任务 |

测试以标准库异步测试和本地 TCP/HTTP 服务为主，不依赖公网在线状态判断回归是否通过。真实网络测量只探测有限的配置端点，分别记录主列表、TCP 和回复链路，避免以全网扫描作为常规测试。

执行 Python 编译检查、适当的格式检查、插件结构检查及关键回归。真实 AstrBot 中验证关键字、命令、首次查询和重载；若本机没有可用实例，明确记为未验证，不能把模拟测试宣称为线上验收完成。

## 风险与待确认事项

- 首次未知名称查询没有现成的名称目录，仍可能必须扫描地址；优化消除无关等待，不能保证所有陌生服务器瞬间找到。
- 激进缩短超时会漏掉高延迟服务器，因此先用统一总预算与优先级改善，再依据数据调低参数。
- 共享任务最容易产生取消传播和结果覆盖问题，必须验证取消、卸载、端点改名和重复探测竞争。
- 缓存新鲜度与连接负载存在取舍，不能通过无限降低刷新间隔换取表面实时性。
- JSON 数据格式带版本，恢复只读已知字段；回退旧插件时允许忽略新缓存重新预热，不要求破坏性迁移。
- AstrBot 生命周期和数据目录 API 需按插件声明的最低支持版本核实；不为方便而无依据提高最低版本。
- 当前计划不依赖新增第三方库。若标准库 HTTP 兼容范围不足以满足实际部署，再以明确失败证据评估依赖调整。

计划完成标准是上述行为得到实现和验证，而非仅新增配置或更改文档。2026-09-10 已执行源码改造与本地验证，具体结果和仍未覆盖的平台验证见 [实施与验证记录](2026-09-10-query-performance-validation.md)。
